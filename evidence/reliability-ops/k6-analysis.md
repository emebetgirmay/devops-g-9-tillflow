**DRI:** Emebet Girmay (`@emebetgirmay`), Reliability + operations · **Date:** 2026-09-29
**Script:** [`services/payments/k6/capacity.js`](../../services/payments/k6/capacity.js) (Payments' G3-4 script, `@chesangJ`)
**Runner:** one-off ECS task `devops-g9-k6` inside the VPC, against the internal ALB ([`infra/envs/sandbox/k6.tf`](../../infra/envs/sandbox/k6.tf), [`run-k6.sh`](run-k6.sh))

## Finding 1: 110 silent 502s (fixed)

**Symptom.** Run 1 passed its thresholds but had 110 failed requests (0.31%), all `502 Bad Gateway` generated by the ALB. Payments' own 5xx count was 0, so the per-service burn alarms (which count `HTTPCode_Target_5XX_Count`) never saw them.

**Root cause.** Exactly 110 tracebacks in `/devops-g9/payments`, all:

```
File "/app/mpesa/fake_adapter.py", line 220, in due_callbacks
    for charge in self._charges.values():
RuntimeError: dictionary changed size during iteration
```

`/_fake/deliver-callbacks` iterated the FakeAdapter's charges while other request threads (`ThreadingHTTPServer`) inserted new ones. The exception escaped the handler, the thread closed the connection without a response, and the ALB answered 502. Customer-facing creates were never affected (all 32,978 checks passed); only the harness endpoint was. The payouts fake had the same pattern.

**Fixes.**

| | Change | PR | Proof |
|---|---|---|---|
| A | FakeAdapter and FakeDisbursements hold a re-entrant lock around shared state | #52 | `services/_shared/tests/test_fake_concurrency.py`: fails 3/3 without the lock (both fakes), passes 5/5 with it |
| B | Any unhandled exception in Payments becomes a JSON 500 with the trace id, an `unhandled_error` log line and a counted 5xx | #52 | `services/payments/tests/test_unhandled_errors.py`: 3 tests, fail without, pass with, including over real HTTP |
| C | Alarms on ALB-generated 5xx (`alb-5xx-fast-burn`, `-slow-burn`) and an overview panel, because the ALB reports these per load balancer only | #53 | Runs 2 and 3: 0 ALB 5xx, panel reads "0 (none)" |

**Cost of the fix.** Run 2 was slower, so we checked whether the lock caused it with a controlled A/B test: the same k6 script against Payments built from just before and just after #52, nothing else different.

## Finding 2: Payments was CPU-bound at 0.25 vCPU (fixed)

At 0.25 vCPU Payments ran at 85–100% CPU under the soak. With CPU pinned, p95 swings widely between runs (229 ms in run 1, 546 ms in run 2, 432–468 ms in the local 0.25-CPU runs), which is what running without headroom looks like. `payments-cpu-high` (over 70% for 10 minutes) **fired at 21:11 UTC and recovered at 21:18 UTC** during run 2, a real alarm from real load (`g3-cpu-high-k6.png`).

**Fix:** Payments to 0.5 vCPU and 1 GB (Fargate's minimum memory for 0.5 vCPU), #55. Run 3: CPU average 26%, peak 55%, p95 154 ms, no alarm.

## Capacity statement

- **Highest sustained rate measured:** 36.7 requests/s over the full 17-minute envelope, with a 15-minute soak at 10 VUs, all thresholds met, on one Payments task at 0.5 vCPU / 1 GB.
- **Headroom:** CPU averaged 26% and peaked at 55% (during the 50-VU spike) against the 70% alarm line: about **2.7x** on the sustained load, but only about **1.3x** on the spike. Memory is not a constraint (22%).
- **Bottleneck:** Payments CPU (a single Python process) and SQLite's single writer. The spike stage produces the long tail (max 7.6 s in run 3, 12.9 s in run 2): writers queue behind SQLite's lock.
- **What this is not:** sizing evidence for production. Per ADR 0009 section 6, SQLite serialises writers; real capacity numbers need the Postgres backend (ADR 0002). Horizontal scaling is not safe on SQLite (each task has its own database), so G3 does not claim autoscaling.
- **Latency by route (run 2, from Payments' own histograms):** `/_fake/deliver-callbacks` ~700 ms (harness only), `/payments` ~120 ms, `/payouts` ~70 ms, `/_admin/sweep` ~60 ms.

## Other defects the G3 work surfaced

| Found by | Defect | Fix |
|---|---|---|
| POS rebuild during #52's release | FastAPI 0.142.0 (released after POS's last build) auto-configures OpenTelemetry when `OTEL_*` is set and exits at start-up (exit 3). The release's smoke check failed and **rolled POS back to revision 24 automatically**; POS stayed up. | #54: pin `fastapi<0.142`; CI now starts the POS image with ECS's `OTEL_*` environment and requires it to come up |
| PR checks #88 | Commission's end-to-end tests used the UTC date as "today" while Commission closes EAT days, so they failed between 21:00 and 24:00 UTC | #56: the tests use Commission's own `business_date()` |
| First `run-k6.sh` attempt | Fargate's scratch volume is root-owned; the k6 image runs as uid 12345 and could not write its script | #51: write to the k6 user's home |
| Deployed stack | The FakeAdapter runs on a manual clock in the sandbox, so callbacks never fell due under load | `ADVANCE_SECONDS` in `capacity.js` (#50) |
